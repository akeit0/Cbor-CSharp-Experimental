# Typed wire values — 2026-10-02

These measurements use the paired graph implementation committed as 37c7d25, before the API cleanup. The wire format and bignum conversion algorithms are unchanged by that cleanup.

`WireValueBenchmarks` measures positive values `(1 << bits) - 1` with 64, 65, and 2,048 magnitude bits. Their preferred CBOR encodings occupy 9, 11, and 260 bytes. The 64-bit case uses a major-type integer; larger cases use tag 2 and a definite byte string. The writer is reused and cleared between operations. Contiguous reads use a span; fragmented reads use a sequence of one-byte segments. Fixture creation, fragmentation, round-trip checks, and runtime-asset assertions run outside measurement.

Sequential BenchmarkDotNet 0.15.8 runs use two launches, five warmups, eight measurement iterations per launch, and 100 ms target iteration time. Host: Windows 11 x64, Intel i7-13700F, SDK 10.0.401. Errors are half-widths of the reported 99.9% confidence intervals. Modern results use the net10.0 asset on .NET 10.0.12. Legacy results use an asserted netstandard2.0 asset on .NET 8.0.31; these are different runtime/asset combinations, not a controlled speedup comparison.

These runs use the initialized buffer-pair formatter architecture. The modern writer intervals are broad, particularly for 2,048 bits; treat those timings as diagnostic estimates rather than precise throughput or speedup evidence. Allocation measurements are reported separately.

Modern definite reads allocate BigInteger's owned limbs without a temporary magnitude array. Warm sequence reassembly adds no managed allocation for these fixtures, but traversing every byte as a segment costs time. Modern writers use bounded stack space for these magnitudes; larger magnitudes rent cleared pooled storage. Legacy APIs require a signed little-endian intermediate array for bignums. The allocation difference is a supported-API boundary, rather than private-layout access. Negative-value magnitude conversion, larger/pool-cold cases, indefinite chunk aggregation, and adversarial inputs still need broader timing coverage. No MessagePack parity follows from these measurements.

An initial legacy benchmark was discarded: BenchmarkDotNet's autogenerated consumer reselected the net8.0 CBOR project asset through transitive project references. The compatibility project now references the built netstandard2.0 assembly explicitly, keeps its project reference only for build ordering, and references Foundation directly. Every benchmark fixture asserts its expected runtime asset; a Dry probe confirms that the incorrect selection fails instead of producing mislabeled results.

Finish builds/tests before benchmarking, and run the suites separately:

```powershell
dotnet run --project benchmarks/Cbor.Benchmarks -c Release -- --filter '*WireValueBenchmarks*' --launchCount 2 --warmupCount 5 --iterationCount 8 --iterationTime 100 --artifacts artifacts/benchmarks/pair-wire-modern
dotnet run --project benchmarks/Cbor.Benchmarks.NetStandard20 -c Release -- --filter '*WireValueBenchmarks*' --launchCount 2 --warmupCount 5 --iterationCount 8 --iterationTime 100 --artifacts artifacts/benchmarks/pair-wire-compat
```

Local reports are retained under the named ignored artifact directories. The measurements cover typed numeric mappings and buffer shapes, not full serializer maturity.
